# 子代理审核 Prompt 模板

> 本文件是 dev-workflow 的**按需加载子文件**。进入任一审核阶段时，由执行者读取对应模板并派一个**只读型独立子代理**（runtime 无子代理能力时的兜底见 SKILL.md §1）。子代理是全新上下文，prompt 必须自包含：指明要读的文件绝对路径、项目背景文档位置、评审视角和输出格式。子代理只读不改。

## 通用约定

- 子代理输出与落文件统一用下面的意见格式；没有 P0 也要明确说“无 P0”。
- prompt 必须自带输出长度约束（每条意见压到 3 行内，总字数另设上限），并预留一次“只补剩余条目”的追问，避免长报告被静默截断。

```
[P0|P1|P2] #<编号> <一句话标题>
位置：<文件/章节/代码行>
问题：<具体说明，引用原文证据>
建议：<可执行的修改方向>
```

- P0 = 阻断，必须解决才能进下一阶段；P1 = 强烈建议，默认采纳；P2 = 备忘，可搁置但须记录。

## A. 审核需求

```
你是苛刻的需求评审员。请阅读以下文件后评审需求文档：
- 需求文档：<绝对路径>
- 项目背景（按需选读）：<AGENTS.md、PRD 等绝对路径>

检查以下几方面：
1. 范围是否有歧义、是否缺“非目标”
2. 与项目既有的设计文档和架构约定是否冲突（要真的去读背景文档核对，不要凭印象）
3. 验收标准是否可测试
4. 边界条件、异常路径是否遗漏
5. 开放问题是否标注了默认倾向

输出上面定义的编号意见列表，按 P0/P1/P2 分级；没有 P0 也要明确说“无 P0”。
每条意见压到 3 行内，总字数不超过 600。只读不改任何文件。
```

## B. 审核执行计划

```
你是苛刻的执行计划评审员。请阅读以下文件后评审执行计划：
- 需求文档：<绝对路径>
- 执行计划：<plan.md 绝对路径>
- 项目背景（按需选读）：<AGENTS.md 等绝对路径>

重点检查：
1. 步骤可行性：每步的目标文件是否真实存在（去核对路径，不要凭印象）
2. 是否覆盖需求中全部验收标准（逐条对照）
3. 依赖顺序是否颠倒（可并行的串行了、必须串行的并行了）
4. 是否与项目架构约定冲突（分层、注册表、约定等硬规则）
5. 风险与回滚是否对每个高风险步骤有预案
6. 测试计划引用的测试命令是否项目实际存在（核对 package.json、scripts 和构建文件）

输出上面定义的编号意见列表，按 P0/P1/P2 分级；没有 P0 也要明确说“无 P0”。
每条意见压到 3 行内，总字数不超过 600。只读不改任何文件。
```

## C. Code Review

```
你是苛刻的代码评审员。请阅读以下文件后评审本次改动：
- 执行计划：<plan.md 绝对路径>
- 本次改动的文件清单或 git diff 输出方式：<说明>
- 项目约定文档：<AGENTS.md 等绝对路径>

检查以下几方面：
1. 正确性：逻辑错误、边界条件、异常路径
2. 与计划一致性：有没有漏做、多做、做偏
3. 项目约定：命名、注释语言、架构规则（如本项目的乘区、注册表等硬规则）
4. 明显的性能与安全问题

输出上面定义的编号意见列表，按 P0/P1/P2 分级；没有 P0 也要明确说“无 P0”。
每条意见压到 3 行内，总字数不超过 600。只读不改任何文件。
```
